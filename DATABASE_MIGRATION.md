# Database Migration: SQLite → Neon PostgreSQL

## 1. Original vs Target

| | Before | After |
|---|---|---|
| Engine | SQLite 3 (single file `server/database.sqlite`) | PostgreSQL hosted on Neon |
| Driver | `better-sqlite3` (synchronous, native module) | `pg` (node-postgres, pure JS, async) |
| ORM | none — raw SQL | none — raw SQL (unchanged approach) |
| Migrations | `CREATE TABLE IF NOT EXISTS` at startup | `migrations/*.sql` + `npm run migrate` (idempotent startup init kept as safety net) |
| Env config | none | `DATABASE_URL`, `DATABASE_URL_UNPOOLED` |

There is **no authentication system** (no users/sessions/roles — all endpoints are open), no background jobs, and no raw-SQL outside `server/src`. The Angular client talks to the API over HTTP only, so no frontend changes were required.

## 2. Architecture & Connection Flow

- `src/database/connection.ts` creates a single `pg.Pool` from `DATABASE_URL`.
  - Pool size: `10` locally, `3` on Vercel (`VERCEL` env), override with `PGPOOL_MAX`.
  - SSL: if the URL contains `sslmode=`/`uselibpqcompat=` the URL drives TLS. Otherwise localhost URLs get `ssl: false` and remote hosts get `ssl: { rejectUnauthorized: true }` (Neon requires TLS).
  - An `error` handler on the pool prevents an idle-client disconnect (e.g. Neon autosuspend) from crashing the process.
- `transaction(fn)` in `connection.ts` wraps `BEGIN`/`COMMIT`/`ROLLBACK` on a dedicated client — used by seeding, `POST /orders/simulate`, `POST /routes/optimize` and `DELETE /customers/:id`.
- `initDatabase()` runs at startup; every request waits for the `dbReady` promise so serverless cold starts are safe.

## 3. Environment Variables

Copy `server/.env.example` → `server/.env`:

| Variable | Purpose |
|---|---|
| `DATABASE_URL` | Neon **pooled** connection (host contains `-pooler`), used by the app. Suffix `?sslmode=require`. |
| `DATABASE_URL_UNPOOLED` | Neon **direct** endpoint, used by `npm run migrate` / `migrate:data`. Falls back to `DATABASE_URL` if unset. |
| `PORT` | Optional, default `3000`. |
| `PGPOOL_MAX` | Optional pool size override. |
| `SQLITE_PATH` | Optional override for `migrate:data` source file (default `server/database.sqlite`). |

Get the strings from Neon Console → your project → **Connection Details** (the pooled host has `-pooler` in the hostname). Never commit `.env` — it is gitignored.

## 4. Schema Changes (SQLite → PostgreSQL)

| SQLite | PostgreSQL | Notes |
|---|---|---|
| `INTEGER PRIMARY KEY AUTOINCREMENT` | `INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | `BY DEFAULT` (not `ALWAYS`) so explicit IDs can still be inserted during data transfer |
| `REAL` | `DOUBLE PRECISION` | lat/lng |
| `TEXT`, `INTEGER`, `CHECK`, `UNIQUE`, `FK` | unchanged | all constraints preserved |
| `orderTime TEXT DEFAULT CURRENT_TIMESTAMP` | `TEXT DEFAULT (to_char(CURRENT_TIMESTAMP,'YYYY-MM-DD HH24:MI:SS'))` | keeps SQLite's text timestamp format; every insert supplies the value anyway |
| `time('now','localtime')` in INSERT | computed in JS (`new Date().toTimeString().slice(0,8)`) | identical `'HH:MM:SS'` local-time semantics |

- camelCase columns (`"orderNumber"`, `"customerId"`, `"boxCount"`, `"orderTime"`, `"assignedRiderId"`, `"deliverySequence"`, `"maxOrders"`) are kept and **double-quoted** in SQL so JSON response keys are unchanged — no frontend changes needed.
- Added indexes: `idx_orders_customer` on `orders("customerId")`, `idx_orders_rider` on `orders("assignedRiderId")` (the only implicit index before was the `orderNumber` UNIQUE constraint).
- Canonical DDL: `server/migrations/001_init.sql` + `002_order_number_seq.sql` (adds `order_number_seq`, used for race-free `orderNumber` generation). The same statements run idempotently in `initDatabase()` — which also holds `pg_advisory_xact_lock` so concurrent cold starts serialize instead of racing on seeds.

## 5. Command Reference

```bash
cd server
npm install
npm run migrate        # apply migrations/*.sql (uses DATABASE_URL_UNPOOLED || DATABASE_URL)
npm run migrate:data   # optional: copy rows from database.sqlite -> Postgres
npm run dev            # start API (auto-creates schema + seeds if empty)
npm run build          # tsc -> dist/
npm run test:smoke     # embedded-Postgres end-to-end API test (no PG install needed)
```

Migration tracking lives in the `_migrations` table; re-running `migrate` skips applied files.

## 6. Data Transfer

No data transfer was required for this migration: the repository has no `database.sqlite`, and the app regenerates identical seed data (13 riders, 30 customers, 28 orders) on first start.

If you have a real `server/database.sqlite` (e.g. an existing local deployment), run `npm run migrate:data` after `npm run migrate`. It copies `customers`, `riders`, `orders` inside one transaction with `ON CONFLICT (id) DO NOTHING` (re-runnable), then advances the identity sequences past the max imported ID and prints source/target row counts for verification. Requires Node ≥ 23.4 (uses built-in `node:sqlite`).

## 7. Local Development

Easiest: `npm run test:smoke` boots an embedded Postgres (downloaded by the `embedded-postgres` devDependency, UTF-8 forced), applies migrations, starts the app and runs 17 endpoint assertions. For a persistent local DB, install Postgres or point `DATABASE_URL` at a free Neon dev branch — `sslmode=disable` is accepted for localhost URLs.

## 8. Deployment (Vercel)

1. Create a Neon project; copy the pooled (`-pooler`) and direct connection strings.
2. In Vercel → Project → Environment Variables set `DATABASE_URL` (pooled) — and `DATABASE_URL_UNPOOLED` if you plan to run `migrate` from CI.
3. Import the repo with **Root Directory = `server`**, deploy, then run `npm run migrate` locally/CI against the production unpooled URL (one deliberate step — never auto-run on boot beyond the idempotent `CREATE TABLE IF NOT EXISTS`).
4. Point `client/src/app/services/api.service.ts` `baseUrl` at `https://<project>.vercel.app/api`.

`pg` is pure JavaScript — no native compilation on Vercel (the previous `better-sqlite3` node-gyp build issue is gone).

## 10. Known Limitations / Remaining Steps

- **Blocked:** production Neon deployment requires you to create the Neon project and set env vars — credentials were not provided, so connectivity to real Neon is unverified (though the `pg` + `sslmode=require` path is the standard documented approach).
- `orders.assignedRiderId` has no FK to `riders` — faithful to the original schema (which also lacked it); add `REFERENCES riders(id)` later if desired.
- `latestPlan` route cache is in-memory per instance, same as before; on serverless it can reset between invocations — call `POST /api/routes/optimize` first.
- `orders.orderTime` remains `TEXT` to preserve the `'HH:MM:SS'` API format; it is not a real `TIME` column.
- Deleting all orders does not reset the identity sequence (same as SQLite behavior where `AUTOINCREMENT` keyword kept the counter); `orderNumber` generation uses `Date.now()` suffixes so no collision occurs.

## 11. Rollback

- The old code is untouched in git history (`git log`); to roll back, check out the previous commit — the app has no destructive schema coupling.
- To reverse a migrated Neon DB: data can be exported via `pg_dump` or `COPY ... TO CSV`; the SQLite data-transfer script is one-directional but the schema maps 1:1 back (`IDENTITY` → `AUTOINCREMENT`, `DOUBLE PRECISION` → `REAL`).
- `migrate-data` never deletes from the source SQLite file (opened read-only), so the original data remains intact as a backup.
